# 编程规范

> 本规范用于 DWF 工作流的技术方案、实现清单、编码执行和迭代实施阶段。进入编码前必须读取本文件，并在任务执行、验证和总结时持续对照。

> 本文件是**通用基线**。若项目级 `.dwf/coding-specs/` 下已有与用户确认的编程规范（如 `前端编程规范.md`、`后端编程规范.md`、`移动端编程规范.md`），本文件作为基线补充；两者冲突时以 `.dwf/coding-specs/*.md` 为准。`.dwf/coding-specs/` 由 `dwf-coding` 在编码前与用户协商生成并确认，与所有 spec/迭代共享，不随迭代重复协商。

## 目标

输出的代码应当能被真实项目长期维护：符合需求、贴近既有代码风格、变更范围可控、验证方式明确。不要为了展示能力而扩大实现范围，也不要把不确定性隐藏在代码里。

## 执行前

- 先读取需求文档、需求分析文档、选定技术方案和实现清单，明确本轮任务的成功标准。
- 如果目标代码目录已有代码，先分析目录结构、技术栈、命名习惯、组件组织、状态管理、接口封装、样式体系和测试方式。
- 如果项目缺少代码且选定方案为 React 前端项目，优先使用 `assets/` 下的模板：
  - PC 端项目使用 `assets/react-pc/`。
  - 移动端项目使用 `assets/react-mobile/`。
  - 通用配置、公共类型、hooks、utils、请求封装等可参考或合并 `assets/shared/`。
- 使用模板时，只复制与选定端和方案匹配的内容到目标代码目录。不要复制无关端模板，不要把 `dist/` 当作源码继续开发，除非用户明确要求保留构建产物。
- 如果模板、技术方案和需求存在冲突，暂停并说明冲突点，不要擅自改换架构。

## 代码风格

- 优先沿用项目已有模式；没有现有模式时，再采用模板中的目录结构和配置。
- 保持命名清晰、职责单一、模块边界明确。避免只有一次使用却增加复杂度的抽象。
- 只修改完成当前任务必须修改的文件和代码；不要顺手重构无关模块。
- 删除不用的代码、导入、变量和配置，避免留下临时调试内容。
- 不硬编码业务可变数据。确需占位时，使用清晰的 mock 数据或 TODO，并在总结中说明。
- 错误处理要可见、可定位。不要吞掉异常，也不要用静默失败掩盖接口、状态或渲染问题。

## React 前端规范

- 组件按职责拆分：页面负责组织，业务组件负责领域逻辑，基础 UI 组件保持通用。
- 状态就近管理；只有跨页面、跨模块或缓存类数据才提升到全局状态或查询缓存。
- 接口访问集中封装，类型定义集中维护，避免在组件里散落请求细节。
- 样式遵循模板和项目现有体系。PC 端优先保证信息密度、可扫描性和桌面交互；移动端优先保证触控区域、纵向节奏和小屏稳定性。
- 确保响应式布局不会出现文字溢出、元素重叠、按钮内容挤压或横向滚动异常。
- 交互状态要完整覆盖：加载、空数据、错误、禁用、提交中和成功反馈。
- 可访问性保持基础可用：语义化结构、可聚焦控件、表单标签、按钮可识别。

## 任务执行

- 严格按实现清单顺序执行。确需调整顺序时，先说明原因，并保持依赖关系清晰。
- 每完成一个任务，按该任务的验证标准检查结果，再把实现清单状态从 `[ ]` 改为 `[x]`。
- 如果发现需求、方案或实现清单不再成立，暂停并告知用户，不要悄然偏离选定方案。
- 对迭代需求，只实施本次迭代确认的受影响范围；未受影响阶段和无关代码保持不变。

## 验证

- 优先运行项目已有的检查命令，例如 lint、typecheck、test、build。
- 前端界面变更应尽量进行浏览器预览或截图验证，至少覆盖目标端的关键视口。
- 如果无法运行验证命令，说明原因，并给出已完成的替代检查。
- 总结时明确列出：完成的任务、修改的主要文件、验证命令及结果、未验证或需用户补充的事项。
